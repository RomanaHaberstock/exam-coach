# Exam Coach – notes for continuing work

Context for AI assistants (and new team members) picking up this project. Read this first.

## What this is

Exam Coach is a student course project (team of students, Austria, winter semester 2026). It's an AI study planner: students upload scripts, slides and old exams, enter exam dates, and get a study plan built backwards from the exam. After study blocks they take quizzes; if they score below where the plan expects them to be, the agent changes the plan by itself (the "feedback loop" is the core idea of the assignment). A "learning profile" (internally: learning fingerprint) measures which study methods work for each student instead of using learning-style labels.

- Live site: https://exam-coach0718.netlify.app (Netlify project "exam-coach0718", deploys automatically from the GitHub repo's main branch). The professor gets this link.
- The team presents the finished product on "Day 3" of the course. A one-page project brief (Word) was already written and sent separately; it describes the product without naming Claude or the hosting.

### Front end (assets/app.js)

- **State** lives in one object `S` (exams, topics, blocks, log, settings, activity, `fp` = learning profile). `normalize()` fills defaults for older saved states; add new fields there.
- **Storage**: IndexedDB key `state` plus `mat-<id>` for extracted material text (`idb` helper, localStorage fallback). No accounts. Backup/restore as JSON under Plan → Your data.
- **Every state change** goes through `commit({ plan, log })`: optionally re-plans, appends a plan-change log entry with per-topic hour diffs, saves (debounced) and re-renders.
- **Planner** `replan()`: keeps done/skipped/past blocks, rebuilds future ones. Backwards: final review on the eve, mock exam a few days before, then retention checks, spaced reviews and learning chunks by urgency across exams. Each learning chunk knows where it starts in the topic's learning time (`from`), so every learn block gets `b.goals` = indices of the topic's goals it covers (`goalSpan()`: the learning time is shared evenly over the goals in order). `place()` merges a learn chunk into the block placed right before it when it is the same exam, topic and day (one longer block instead of "Learn: X" twice in a row; goals joined), but never beyond the "Block length" setting (`S.settings.blockMin`, 45/60/90; also the chunk size): the previous block is filled up to it and the rest becomes the next block, so same-day pieces of 15+60+30 become 60 + 45, not 105 or three blocks. A rest under 15 minutes is avoided by filling the previous block less. `place(d, minutes, props, goalsAt)` gets `goalsAt(offset, len)` from the learning step, so each part of a split chunk gets the goals of its own minutes. **Spacing beyond the first review**: after the 2-day retention check and the first spaced review (`GAPS[1]`), every learned topic keeps getting reviews until the eve (`later[exam]`, `pushLater()`): the next one waits about as long as the topic has been known (`nextGap(L, d)` = max(`GAPS[1]`, days since learned × forgetting factor from the profile), so 6 → 12 → 24 days). Already learned topics start from `lastSeen()` (latest done review/check, also inside a mixed block, or quiz). Step 4 places at most one such review per exam and day, before learning: the topics due (most overdue first), topped up with topics due in the next 2 days, max 3 → "Mixed review: A, B, C" (45 min, `b.mix` = the other topic ids, `b.since` = days since learned) or "Spaced review: A" (30 min) when only one is due. Step 5: once an exam's learning is all placed, free days between the last learning block and the mock get an "Exam practice: A + B" block (`type: "review"`, `practice: true`, `mix: [B]`) every other day, two topics per block in turn by exam points (the pairing shifts each round for an even number of topics), so the last weeks aren't empty (learning is front-loaded by urgency). `futureByTopic()` shares a block's minutes over all its topics (`mixTopics(b)`). `assignMethods()` picks a study method per topic (experiments until each method has 2 retention checks, then best method, every 5th topic re-tests).
- **Feedback loop** `applyQuizResult()`: compares score with expected mastery (target × learning progress); below −10 points adds study time + repair review; well above frees time. A topic not fully learned that scores under target − 10 but not under expected − 10 gets verdict `notyet` ("Not learned yet (x% of its study time done), so this doesn't count as behind…"); mocks list these in a separate "Not learned yet" group, not under "On track". `commit()` accepts `log.detail` as a function of the change list, and `keepText()` only says "The plan stays as it is" when the list is empty. The eve's final reviews go to topics by `eveRank()` (behind plan first, then unquizzed/on-track by weight, clearly strong last), so a result that changes nothing doesn't move the eve slot.
- **Points per hour** `topicPoints()` / `pointsTable()`: exam points per topic (from AI-found old-exam tasks `e.oldTasks`, else the last scored mock, else old-exam hits, else weights) and points per remaining study hour. Each exam has `mode` (`"top"` default, or `"pass"` with `passPct`, default 50). `learnOrder()`: the **material order** (the topic list, which the AI returns in learning order) is the default sequence; repair topics (`extraMin > 0`) first. Top grade = material order. Pass = the topics `pointsTable()` marks as needed (cheapest points per hour until the pass mark) first, in material order, then the rest in material order. `topoOrder()` then pulls each topic's prerequisites in just before it, so links override the material order (pass mode also marks unfinished prerequisites of needed topics as needed, `r.first`). "Hours left" for a learned but not mastered topic = effort × (1 − level), rounded to half hours. The built-in example exams have prerequisite links (`exampleTopics()`). Shown under Exams & materials → "Where your time pays off".
- **Confidence calibration → extra check** `calibrate()` (called by `applyQuizResult(e, t, score, missed, src, { sureWrong })` from `gradeQuiz()`): two answers marked "sure" that were wrong in one quiz, or one when the topic's last "sure" answers (4+) were right under `CAL_ACC` (70 %), set `t.calCheck = { due: +2 days, set, concepts }` → `replan()` places a 15-min "Extra check: X" review (`reviewKind` `"calib"`); done block or the next quiz on a later day clears it; dropped a week after it was due. A below-plan result only says the repair review covers them. The log says "You were sure about 2 answers that were wrong (…)… a 15-min extra check of X comes in 2 days." (no "plan stays" ending then).
- **Review deck (local spaced repetition)** section `review deck`: per exam `e.cards = [{ id, topicId, front, back, src: "quiz"|"exam"|"cards", box 1–5, due, added, seen, lapses, last }]`. Sources: quiz and practice-exam questions scored under 0.7 or answered right with "guess" (`cardsFromAnswers()`; mc cards list the options, the back starts with the right one), and flashcards made on the Study page (`genStudy()` → `addCards()`; known at the first try there → box 2, `deckFirstTry()`). Same front text = same card (a missed one goes back to box 1). Leitner: knew → box + 1, missed → box 1 (and once more at the end of the session); next due `LEITNER[box]` = 1/3/7/14/30 days, never after the eve (`cardDue()`). Today shows `deckPanel()` (`#deck`); `startDeck()` → view `cards` (`vCards()`, `DK` in memory, max `DECK_DAY` = 20 cards, interleaved one topic at a time by `dueCards()`). No AI call at all. Self-rated, so `finishDeck()` only moves mastery `DECK_WEIGHT` (15 %) towards the share known at the first try, for topics with a quiz score and ≥ `DECK_MIN_TOPIC` (3) cards; it's logged (`kind: "cards"`) and re-plans, but never goes into `fp.quizLog` (no effect on the method comparison, retention checks or time of day). `S.activity[d].cards` ≥ 10 counts for the streak. `cleanCards()` (via `normExam()`) drops broken/orphaned/duplicate cards and clamps box/dates for restored backups; max `DECK_MAX` (400) per exam (best-known oldest dropped first). Cards leave with their exam (new semester, delete).
- **Prerequisites** `t.prereqs` (topic ids this topic builds on; "Builds on" multi-select in the topics table, `t.prereqsSet` once the student edits it). `cleanPrereqs()` (called by `normExam()`, after analysis and topic removal) drops unknown/self links and breaks cycles: hand-set links first, then links to earlier topics, then later ones. Root-cause diagnosis in `quizEffect()`: if a below-plan topic has a weak prerequisite (`weakPrereq()`: quizzed below target −10, or not quizzed and not fully learned), most of the repair time and tomorrow's repair review go to the prerequisite, the topic itself is reviewed the day after, and the log says "Your trouble with X probably comes from Y — reviewing Y first." Mock exams process topics prerequisites-first and repair a prerequisite only once (`ctx.repaired`).
- **Mock exam scoring** `vMock()` / `applyMockResult()`: points per task (pre-filled from old-exam tasks, last mock or topic estimate), mapped to topics; per-topic % go through `quizEffect()` (the shared core of `applyQuizResult()`) against target × learning progress, like a quiz (a half-learned topic still has its learning time planned, so it isn't repaired twice), logged as one `kind: "mock"` plan change. Stored on the block as `b.mock` (with the energy level of that day's check-in) plus `b.mock.fx`: per topic the extra minutes added and mastery / repair-review date before and after. A scored mock can't be undone (Undo shows a message); "Edit results" on the results view calls `reverseMock()` (subtracts the extra minutes, restores mastery and review date unless a later quiz changed them, removes its quiz entries by `mockId`) and then applies the new points. Mocks scored before `fx` existed can't be edited. `replan()` places no new mock once one for that exam is done or scored. Per-topic mock results go into `t.quizzes` with `mock: true`, so they count for mastery but not for the review's quiz trend. Only real quizzes and Teach the AI / oral exam results go through `logQuiz()` (which records the energy level) into `fp.quizLog`.
- **Learning profile** `fingerprint()`: method retention (quiz 2 days after finishing a topic), forgetting speed (immediate vs. retention score → second review gap), time of day, plan completion rate, focus span (Pomodoro sessions), confidence calibration (sure/unsure/guess on quiz answers), enjoyment ratings, energy vs. results. `loadDemoFingerprint()` adds clearly marked example data (`demo: true`). Topics with a learning block done as a "Go lighter" session (`b.light`, see `wentLighter()`) are left out of the method comparison: their quizzes are logged with `light: true` and don't count for method retention, immediate scores or pending checks, so `assignMethods()` isn't skewed.
- **Energy check-in**: `startFocus()` (timer phase `checkin`) and the Study page ask low/OK/high once per session; entries go to `S.fp.energy` and are matched to blocks by id or topic+type (re-planning changes block ids). Quizzes within 4 h and focus sessions carry the level. Low energy offers a lighter session (flashcards instead of new material via `studyMethod()`, `lightFocusMin()` Pomodoro).
- **Post-exam review**: after an exam date passes, the Today page asks for the result: an optional Austrian grade 1–5 (`e.review.gradeNum`, `GRADES`), a free-text result (`grade`) and what helped/didn't, with frozen `examStats()` (study time, quiz trend, best method, readiness, latest mock score). At least one of the two grade fields is needed. The summary shows the numeric grade next to the readiness the plan predicted, and the mock score if there is one (`reviewStats()` adds a mock scored after the review). "Start a new semester" (`startSemester()`) moves finished exams to `S.archive` (incl. topic ids, `oldTasks`, mode/pass mark and every scored mock as `mocks`), deletes their blocks and material texts, and keeps `S.fp` (past block counts go to `fp.realismPast`). `normalize()` → `normExam()` / `normSemester()` fill defaults for all of this, also for restored backups.
- **Restored backups**: `normalize()` coerces block `status`/`type`/`minutes` and mock task points, drops a malformed `mock.fx`; `statsList()` and `blockRow()` also coerce numbers (`numOr()`) and escape ids, so crafted backups can't inject markup.
- **Today page**: "Did you do these?" only lists past open blocks of exams that are still ahead; a finished exam gets its review form instead.
- **Header and mobile**: up to 767 px the sections are a tab bar fixed at the bottom (`#nav`, 7 columns incl. How it works, 56 px tall, SVG icon + short label: `.long`/`.short` spans, e.g. "Exams & materials" → "Exams", "How it works" → "How"); the header keeps only the brand and the streak chip (save state hidden). 768–1099 px: one header row with short tab names (How it works stays long) and the chip without its "· keep it today" part (`.keep`, still in the chip's `aria-label`). ≥ 1100 px: full names. The streak chip and save state are stacked in `.topstat` on the right, so tabs, chip and save state are always one row (test "the header keeps all seven tabs…"). Up to 767 px the timer pill/card, the toast and the tour card sit above the bar (the tour scrolls its step's element under the header itself — `go()` skips `scrollTo(0, 0)` while `TOUR` is active — and `tourPlace()` moves the card to the top, `.tour-up`, when the page can't scroll far enough to keep the element above it; test at 375×740). Don't give page elements the class `top` (= the sticky header; the profile's best bar is `.hbar.best`). `main` gets bottom padding for the bar plus the open timer (`renderTimer()` sets `--timer-h` on `<body>`). The mock form (`#mk-table`) and the topics table (`#topics-table`, `.tt-wide` cells span the card) show one small card per row (`data-label` on cells). Phone-only layout (≤ 560 px): block rows put date/time/length on one line. On touch screens (`pointer:coarse`) and phones every `.btn`, field, quiz option and pill is at least 44 px tall.
- **Accessibility** (WCAG AA basics; tests: "colour tokens meet WCAG contrast…", "works with the keyboard…", "fits a 375 px phone on every view…"): every `data-act`/`data-view` control is a `<button>` (keep it that way: the keyboard test fails on any other element). Colour tokens are checked from the page in both themes: text pairs ≥ 4.5:1, field borders `--field` ≥ 3:1 against surface and bg. Token roles: `--hl` = the yellow highlight behind text (brand, hero, streak number; a deep gold in dark mode, because light text on `--mark` is 1.5:1 there), `--on-strong` = text on a filled `--bad`/`--good` (timer pill; dark text in dark mode). Light `--good`/`--warn`/`--bad` were darkened (#17724A/#8F5606/#B0302B) so chips reach 4.5:1. **Focus**: `render()` rebuilds `#main`, so it remembers the focused control (`focusKey()`: id, else tag + data-* attributes) and focuses it again; if that control is gone, the view's `[data-autofocus]` control (review cards: Show answer → Knew it → next card's Show answer), else `#main`; a `change` fired by Tab re-renders before the focus moves, so `changedEl` + the last Tab key (`lastTab`) move focus on to the next/previous control. `go()` focuses the view's first heading (`focusHeading()`, tabindex -1). Skip link "Skip to content" before the header. `:focus-visible` = 3 px accent outline (ink on primary buttons; quiz options and pills show it via `:has()`). **Screen readers**: one polite live region `#live` (`role=status`, outside `#main`); `toast()` and any new spinner text after a render (progress, "Grading…", `lastBusyText`) go through `announce()`. `#timer` is not a live region (it re-renders every second; phase changes come as toasts). Quiz/practice questions have ids (`qt-i`/`pxt-i`); options are a `role=radiogroup` and written answers are `aria-labelledby` the question; after grading `optTag()` writes "Correct answer" / "Your answer · wrong" next to the coloured options. Inputs without a visible label get `aria-label` (topic fields, new topic, remove buttons name the topic). `prefers-reduced-motion` turns off all animations/transitions.
- **Progressive disclosure**: long block lists (Plan day by day, Today's list and "Next up") fold each block's content into `<details class="more"><summary>What to do</summary>` (`blockRow(b, { fold: true })` → `foldDetail()`); the "Do this now" card and the Study page show it open. Only blocks due today or earlier get primary buttons (`pri` in `blockRow()`), so a page has one obvious next action. When nothing is planned today, the "Do this now" card names the next block, folds its content and offers "Start it early" for a learning block. The Today page order: alerts → reviews → Do this now → today's blocks → streak → learning fingerprint teaser → exams → latest changes (streak and fingerprint buttons are not primary).
- **AI calls**: always through `AI.json(prompt, opts)` → `aiCall()` → POST `/api/ai`, which returns server-sent events in Anthropic's format (`content_block_delta`, `message_delta`, `error`). Errors are objects `{ code, detail, fallbackTried }`; user-facing text comes from `aiError()` (busy: "The AI service is overloaded right now (this happens on the free plan at busy times). Your work is kept — try again in a minute."; `stream_broken`: "The connection to the AI broke off. Your work is kept — try again."; `rate_limited` with `fallbackTried` (the backend's error event has `fallback: true`): "The free AI quota is used up for now (a quicker backup model was tried too)…"), which never names the provider, hosting or env vars ("Ask the person who runs this Exam Coach…"); `aiDetail()` strips product/host names from the technical detail. `aiCall()` gives code `stream_broken` when reading the stream throws half-way (reset) or the stream ends without a stop reason or error event (the backend always sends one of them). `aiCall()` also sends `think` (`"default"` only for the material analysis = the model's own thinking level; otherwise the backend uses low thinking) and `maxTokens` (output limit for this answer); an answer that ends with `max_tokens` and no text gives code `truncated` ("The AI's answer was cut off…"). `AI.json(prompt, { salvage: true })` keeps the complete list items of a cut-off or broken answer (`salvageJSON()`: closes the brackets after the last complete array element; sets `opts.cut`); without `salvage` a cut-off answer is an error.
- **Generating lists** (quiz, practice exam, flashcards, practice problems) goes through `genList(build, n, { key, signal, onRetry })`: `listOf(res, key)` finds the list in any wrapper (bare array, `{"quiz":{"questions":…}}`), every item is checked on its own (`cleanQuestion()`: question text required; type names normalised; mc needs 2–6 non-empty options and an answer given as index, "B" or the option's text, else the question is dropped; written questions need a model answer), and if the answer was cut off/unreadable/empty (`GEN_RETRY`) or fewer than half the items are usable, the request is sent once more for `fewer(n)` = ⌈n/2⌉ items (min 2), keeping the better answer. Busy/quota errors are not repeated (the backend did). Output limit `genTokens(n)` = 4000 + 900 per item. The quiz and study material send `QUIZ_CTX` (30k chars) of material. The page says when fewer questions came ("The AI wrote 3 of the 5 questions…", `quiz.note` / `PX.note`) and while retrying ("The first answer couldn't be used, so the AI is trying again with 4 questions…"). After two failures: "The AI's answer was cut off or couldn't be read, also on a second, shorter try. Your work is kept — try again in a minute." The worked example (one object, no list) is asked for once more on the same errors.
- **AI usage on the shared quota** (section `AI usage: saved answers, question bank, availability`; numbers in "AI calls and quota" below):
  - **Saved answers** (`cacheGet`/`cachePut`/`cacheDrop`, IndexedDB `aic-<key>` + index `aic-index` with `{ at, examId, kind, topicId }`, newest `AIC_MAX` = 80 kept; memory only without IndexedDB). Keys use `hashStr()` (cyrb53; `crypto.subtle` doesn't exist on http pages). **Analysis**: per part, key = hash of `[ANALYZE_V, analysisPrompt(e with date/target blanked, digest, part)]`, i.e. the files' text, the subject/format, the part layout and the topics known from earlier parts — so re-analysing the same files costs nothing, and when only a later part changed, the earlier parts are reused. The log/toast/`#analyze-cached` say so; "Ask the AI again" (`analyze-fresh` → `analyzeMaterials(e, true, true)`) skips saved answers. **Study material** (flashcards, practice problems, worked example): `studyKey()` = `[STUDY_V, exam, topic, method, the block's goal texts, matKey(e)]`; a saved set opens with "Saved from an earlier session…" and "New ones from the AI" (`s-gen-fresh`); flashcards come in a new order. Bump `ANALYZE_V` / `STUDY_V` when a prompt changes so old answers aren't reused. Removing a file (`materialsChanged()`), deleting an exam or starting a new semester drops the exam's saved answers.
  - **Question bank** `t.bank = [{ q, at, asked, wrong, last }]` (max `BANK_MAX` 40, `cleanBank()` in `normExam()` re-checks every question with `cleanQuestion()`, so backups can't inject). `generateQuiz(e, t, n, fresh)` takes questions from `bankPool()` first: never asked ones (weak concepts first), then ones answered wrong on an earlier day; a question answered right is never asked again (repeating it would measure memory of the question, which would inflate mastery for the feedback loop). Questions are shuffled and mc options reordered (`shuffleOptions()`, the answer index follows). Only when the bank has fewer than n does the AI write a quiz, and then n + `BANK.extra(n)` (⌈n/2⌉, max 4) questions: the material in the prompt is the expensive part and costs the same, so the extras are nearly free; all go into the bank. `bankMark()` after grading. Practice exam (all topics): `genPractice()` builds it from the bank when every allocated topic has enough questions, and its questions go into the topics' banks as asked. Removing a file drops unasked questions (they may come from that file), keeps missed ones. "New questions from the AI" (`gen-fresh`) skips the bank.
  - **Question bank vs. review deck** (two different things; a missed question goes into both): the **bank** (`t.bank`) is for *quizzes*: which AI-written questions a future quiz may use, so the AI isn't asked again; a quiz from the bank is a real quiz (score → `applyQuizResult()`, `fp.quizLog`). The **deck** (`e.cards`) is for *self-review* without any quiz: Leitner cards with the answer on the back. A missed question: bank `wrong` (asked again in a quiz from the next day on) + a deck card in box 1 (due tomorrow). Mastery counts the miss once, through the quiz score; the deck only nudges mastery when a card session is finished (`DECK_WEIGHT`). Bank questions come back with their options reordered, so `cardsFromAnswers()` finds the existing card by its question (`cardOfQuestion()`, not by the whole front) — missed again: that card goes back to box 1 (no second card); answered right (not guessed): it moves up one box, at most once a day, without touching mastery (the quiz score already counts).
  - **Example questions = example bank**: `exampleExams()` calls `seedExampleBank()` (demo.js), so every `EXAMPLE_QUIZ` question is in its example topic's bank; `demoCards()` marks the questions missed in the example history as asked + wrong on that day. "Use the example questions" (`exampleLeft()`) asks the built-in questions not answered right yet; when all were answered right it says so (`#example-done`) instead of the button. "Generate quiz" on an example topic also takes them from the bank first, so the demo still needs no AI request.
  - **Quick model** (`modelTier: "quick"`): short-answer grading in `gradeOpenAnswers()` (comparison with a model answer; any calculation in the batch, or any answer mentioning grader/AI/KI/points/Punkte/marks/score/%/Note/Bewertung (`GRADING_WORDS`), keeps the main model, which spots requests for points better) and the summary feedback `studyFeedback()`. Analysis, question/study-material generation, teach/oral keep the main model (quality). On the free tier each model has its own quota, so this also spreads load; the backend falls back quick → default (and default → quick).
  - **AI unavailable** (`aiDown = { code, until, n }`, set by `noteAiFail()` in `aiCall()` for `rate_limited` / `busy` / offline, cleared by any successful answer): one banner `#ai-down` at the top of every view (`aiBanner()`: why, when it tries again — the backend passes the provider's "retry in" seconds as `retryS`, else 60 s; a third quota failure in a row says "probably for today" — and `NO_AI_WORKS`: plan, timer, saved questions/flashcards, mock scoring by hand), with "Try again now" (`ai-retry`). Also shown when the AI is off (`aiState === "off"`) and on the browser's `offline` event. While it is down, `askAI()` (every AI request goes through it) sends nothing and fails with `no_ai`/`offline` (message = `aiOffMsg()`); AI buttons are disabled via `aiReady()` (Analyse and "Ask the AI again" too). Accessibility: the banner is a labelled region (`role=region`, `aria-labelledby="ai-down-h"`), going down / coming back is announced in `#live`, and disabled AI buttons (`AI_ACTS`) get `aria-describedby="ai-down-msg"` in `render()`. On the quiz page of an example topic with the AI unavailable, "Use the example questions" is the one primary button (Generate quiz isn't). The analysis' own retry after its countdown passes `force`. Quizzes and practice exams still come from the bank (a shorter quiz if the bank has ≥ 2 questions), saved study material opens.
  - **Self-rating**: when the AI can't grade written answers (any request error, incl. unavailable or Stop), they are no longer counted as 0 (which made the feedback loop add repair time for an outage): the quiz / practice exam goes to phase `"self"` (`selfNotice()`, `selfBox()`: model answer + Right / Partly / Wrong = 1 / 0.5 / 0, `selfRate()`), then `finishQuiz()` / `finishPractice()` continue as before. ### Backend (netlify/edge-functions/ai.js)

- Providers: `gemini` (default, free tier) and `anthropic` (paid). The fallback model is the other tier's model (default → quick, quick → default), so a quick request whose quota is used up gets the main model once. Chosen by `AI_PROVIDER`, otherwise by which key exists.
- Env vars (set in Netlify → Project configuration → Environment variables): `GEMINI_API_KEY` (set on the live site), optional `ACCESS_CODE`, optional `ALLOWED_ORIGINS` (comma-separated extra origins allowed to call `/api/ai`), `GEMINI_MODEL` (default `gemini-3.8-flash`), `GEMINI_MODEL_QUICK` (default `gemini-3.5-flash-lite`), `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, `ANTHROPIC_MODEL_QUICK`.
- The response stream starts immediately (`: connected`) with a keep-alive comment every 5 s (`STREAM.keepAliveMs`), because Netlify cuts off functions that don't start answering within ~40 s. On 500/502/503/529 `fetchWithRetry()` retries up to 3 times after `RETRY.delaysMs` (2 s, 5 s, 10 s + up to 0.5 s jitter; ~18 s worst case, keep-alives keep flowing), then tries the quick model (`*_MODEL_QUICK`) once if it differs from the model asked for; if that fails too, the first model's error is reported. Each retry is logged with `console.log` ("Exam Coach AI retry: …"). Tests replace `RETRY.sleep` so they don't wait. Provider errors become `error` events with a code (`rate_limited`, `busy`, `bad_key`, `model_unavailable`, `prompt_too_large`, `upstream_error`) and a neutral message like `429 rate limit: …`; the full message with the provider name is logged with `console.log` (visible in Netlify's function logs).
- Hardening: body over 1.5 MB is refused (413) by `content-length` before parsing and again while reading (chunked); prompts over 200,000 characters too (the page's largest request is ~90,000: `ANALYZE_CHARS` + instructions). A browser `Origin` from another host gets 403 (no Origin = allowed). `ACCESS_CODE` is compared via SHA-256 + constant-time loop. Best-effort in-memory limits per client IP (`context.ip`): 120 AI requests/min (POST only; the GET status check never counts against it) and 30 wrong access codes per 10 min, generous because a whole class can share one university Wi-Fi IP. During a code lockout, requests carrying a code get 429, but a GET status check without a code still answers. Per edge isolate only, so not a real quota. `ACCESS_CODE` stays optional; whether to set one on the public site is the team's decision.
- A 429 (quota/rate limit) is not retried with the same model (those limits last a minute or a day); the quick model gets one try right away (free-tier quotas are per model), logged as "… answered 429 (quota or rate limit); trying … instead". Error events for 429/503 carry `retryS` when the provider says when to try again (`retryAfter()`: "Please retry in 41.7s", RetryInfo `retryDelay`, or `Retry-After`). If the fallback also fails, the first error is reported with `fallback: true` in the error event (`fetchWithRetry()` returns `{ res, fallbackTried }`; also set for the busy fallback).
- If reading the provider's answer fails half-way, the error event has code `stream_broken` ("The AI's answer broke off: …"). When the page closes the connection, `ReadableStream.cancel()` aborts the provider request (`signal` passed to `fetch` and `pipe()`), so no CPU is spent on an answer nobody receives.
- CPU budget (Netlify: 50 ms CPU per request; above it, or when the isolate dies, the page only sees a reset stream): the body is collected as bytes and decoded/parsed once (`readLimited()`), the provider request body is built once per model (Anthropic: cached per model; retries send the same string), and `geminiParser` is linear (searches only new text, joins an event's pieces once). Unhandled promise rejections would end the whole isolate (and every answer it is streaming): `drop()` catches `cancel()` rejections, and on Deno an `unhandledrejection` listener logs instead of crashing.
- Gemini's stream is converted to the same event format (`geminiParser`), thought parts are dropped, `responseMimeType: application/json`.
- **Thinking and output limit**: on Gemini, `maxOutputTokens` counts the hidden thinking too (Google's thinking docs); Gemini 3.8 Flash thinks at "medium" by default (3.x Flash-Lite: "minimal"; thinking can't be turned off on Gemini 3). The body's `think` (`"low"` default, `"default"` = the model's own level) goes through `thinkingFor(model, think)`: Gemini ≥ 3 (not Flash-Lite) → `thinkingConfig: { thinkingLevel: "low" }`, Gemini 2.5 → `thinkingBudget` 0 (Pro 128), others nothing. A model that answers 400 mentioning "think" is asked again without the setting. `maxTokens` from the page is clamped to `OUTPUT` (2,048–32,768; default 32,768; Anthropic max 16,000). Bodies are built once per model. `geminiParser` logs "Exam Coach AI: Gemini finished with MAX_TOKENS after N characters of answer; tokens: prompt …, thinking …, answer …" for every answer that didn't end with STOP or had no text — look for these in Netlify's function logs when a generation fails.

## Working conventions

- Keep it build-free: no frameworks, no bundler, no external CDNs (the CSP blocks them). Vendor any new library into `assets/vendor/`.
- Run `npm test` after every change (first time: `npm install && npx playwright install chromium`). Add a test for new behaviour. ### Stream resets: what was measured and what is guessed

- **Measured locally** (Node, `process.cpuUsage()` around `handle()`, fake provider): largest allowed request (~199k chars, ~280 kB body with umlauts) + 4k-char answer ≈ 2–4 ms CPU; with a 120k-char answer ≈ 8–15 ms (incl. the test harness); first request in a fresh process ≈ 7–10 ms. Pieces for 280 kB: JSON.parse 0.4 ms, decode 0.3–0.5 ms, JSON.stringify of the provider body 0.5 ms, encode 0.2–0.3 ms. A normal analysis answer (a few kB) is negligible. So for the requests the page sends, CPU stays well under 50 ms.
- **Found**: the old `geminiParser` appended to one buffer and re-ran `replace`/`indexOf`/`slice` on it for every network piece: quadratic in the size of one event. One 200 kB event in 256-byte pieces cost 31–57 ms CPU (over the limit on its own); now 0.7 ms. Big single events happen when Gemini sends a JSON answer in one chunk; analysis answers are usually smaller, so this is a possible but not proven cause.
- **Guessed, not verifiable without Netlify logs**: the isolate being stopped (CPU limit, an unhandled rejection, platform recycling), or a network drop on the student's side during a 1–2 minute request. Netlify documents only the 40 s header timeout and 50 ms CPU; no wall-clock limit for a streaming response. Look in Netlify's function logs for "Exam Coach AI" lines around the time of a reset.
- **Why `ANALYZE_CHARS` stays 80k**: CPU doesn't depend on it in a relevant way (≈1 ms per 100 kB). Halving it would double the requests per analysis (130-page deck: ~3 → ~6) on the one key the whole class shares (requests-per-day quota), and the topic merge gets worse with more parts. The per-minute token quota is now handled by the quick-model fallback, and a part that breaks off is retried in 26k parts automatically, so smaller requests are used exactly when big ones fail.

## AI calls and quota (measured 15 Nov 2026)

Instruction text measured with the example exam (characters, without material): analysis 2.1k (later parts 2.6k with known topics), quiz 1.1k, study base 0.5k, practice exam 2.3k, teach 2.4k, oral 2.2k; every request adds `MATH_RULES` (0.7k) and the system line. Tokens ≈ characters / 4 (English; German text more like / 3.5). Output tokens are estimates from the answer shapes (not measured against Gemini). The GET status check (`checkAI()`, on load) uses no tokens.

| Call (function) | When | Input | Output (estimate) | Model / thinking |
|---|---|---|---|---|
| Material analysis, per part (`runAnalysis()`) | Once per exam setup; parts = text / 80k (130-page deck ≈ 200k chars → 3) | ≤ 80k material + 3k ≈ **≤ 21k tok** | 2–5k answer + model's own thinking | main, `think: "default"` |
| Quiz (`generateQuiz()` → `genList()`) | After learning a topic, retention check, any time | ≤ 30k material + 2k ≈ **≤ 8k tok** | ~300 per question (limit 4000 + 900/q) | main, low |
| Grade written answers (`gradeOpenAnswers()`) | Each quiz / practice exam with written answers | 1.5k + ~0.6k per answer ≈ **0.5–3k tok** | ~150 per answer | **quick** (calc: main), low |
| Flashcards / practice problems / worked example (`genStudy()`) | Study page of a learn block | ≤ 30k + 1.5k ≈ **≤ 8k tok** | 1.5k / 2.5k / 1.5k | main, low |
| Summary feedback (`studyFeedback()`) | Summary / explain blocks | ≤ 30k + ≤ 6k text ≈ **≤ 9k tok** | ~0.4k | **quick**, low |
| Teach the AI (`teachPrompt()`) | 1–2 calls per session | 24k + 2.4k + ≤ 10k ≈ **7–9k tok** each | ~0.6k | main, low |
| Oral exam (`oralPrompt()`) | 4–6 calls per session | 24k + 2.2k + transcript ≈ **7–12k tok** each (~45k per session) | ~0.15k per question, 0.4k at the end | main, low |
| Practice exam (`genPractice()`) | Before the mock | ≤ 40k + 2.3k ≈ **≤ 11k tok** | ~0.3k per question (12 → ~3.6k) | main, low |

**Typical student**: setup ≈ 3 analysis requests, ~65k input tokens (plus re-analyses, which used to cost the same again). A study day ≈ 1 quiz + 1 grading + 1 study material + 1 feedback/teach ≈ 4 requests, ~27k input / ~5k output tokens. A class of 30 on one key: ~90 requests / ~2M tokens for setup, ~120 requests / ~0.8M tokens per study day. On the free tier the requests-per-day and tokens-per-minute limits per model are what runs out (13 Nov: 429 on a ~78k-character analysis).

**Savings from the quota work (estimated, not measured live):** re-analysing the same files: 100 % (was a full re-run, e.g. after a failure or a date change); a quiz pressed again without answering: 100 %; quizzes: the extra 2–4 questions usually cover the next quiz on the topic (the retention check 2 days later gets the unused and missed ones), so about every second quiz request on a topic is saved (~8k input tokens each) for ~1k extra output tokens; study material reopened after a reload or on another day: 100 % (it used to live only in memory); grading and summary feedback (≈ 2 of 4 daily requests, small inputs) move to the quick model's separate quota; after a quota error, students clicking again no longer send requests (each used to cost 2 provider calls: main + fallback) until the retry time. Overall, for normal studying roughly a third fewer requests and input tokens on the main model; more for students who re-analyse or revisit study blocks. Not shared between students (each browser has its own cache); see ideas.
