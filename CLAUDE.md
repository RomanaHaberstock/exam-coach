# Exam Coach – notes for continuing work

Context for AI assistants (and new team members) picking up this project. Read this first.

## What this is

Exam Coach is a student course project (team of students, Austria, winter semester 2026). It's an AI study planner: students upload scripts, slides and old exams, enter exam dates, and get a study plan built backwards from the exam. After study blocks they take quizzes; if they score below where the plan expects them to be, the agent changes the plan by itself (the "feedback loop" is the core idea of the assignment). A "learning profile" (internally: learning fingerprint) measures which study methods work for each student instead of using learning-style labels.

- Live site: https://exam-coach0718.netlify.app (Netlify project "exam-coach0718", deploys automatically from the GitHub repo's main branch). The professor gets this link.
- The team presents the finished product on "Day 3" of the course. A one-page project brief (Word) was already written and sent separately; it describes the product without naming Claude or the hosting.

### Front end (assets/app.js)

- **State** lives in one object `S` (exams, topics, blocks, log, settings, activity, `fp` = learning profile). `normalize()` fills defaults for older saved states; add new fields there.
- **Storage**: IndexedDB key `state` plus `mat-<id>` for extracted material text (`idb` helper, localStorage fallback). No accounts. Backup/restore as JSON under Plan → Your data.
- **Every state change** goes through `commit({ plan, log })`: optionally re-plans, appends a plan-change log entry with per-topic hour diffs, saves (debounced) and re-renders.
- **Planner** `replan()`: keeps done/skipped/past blocks, rebuilds future ones. Backwards: final review on the eve, mock exam a few days before, then retention checks, spaced reviews and learning chunks by urgency across exams. Each learning chunk knows where it starts in the topic's learning time (`from`), so every learn block gets `b.goals` = indices of the topic's goals it covers (`goalSpan()`: the learning time is shared evenly over the goals in order). `place()` merges a learn chunk into the block placed right before it when it is the same exam, topic and day (one longer block instead of "Learn: X" twice in a row; goals joined), so a learn block can be longer than the "Block length" setting (`blockMin` is the chunk size); Pomodoro breaks still split it. Step 5: once an exam's learning is all placed, free days between the last learning block and the mock get an "Exam practice: X" block (`type: "review"`, `practice: true`) every other day, topics in turn by exam points, so the last weeks aren't empty (learning is front-loaded by urgency). `assignMethods()` picks a study method per topic (experiments until each method has 2 retention checks, then best method, every 5th topic re-tests).
- **Feedback loop** `applyQuizResult()`: compares score with expected mastery (target × learning progress); below −10 points adds study time + repair review; well above frees time. A topic not fully learned that scores under target − 10 but not under expected − 10 gets verdict `notyet` ("Not learned yet (x% of its study time done), so this doesn't count as behind…"); mocks list these in a separate "Not learned yet" group, not under "On track". `commit()` accepts `log.detail` as a function of the change list, and `keepText()` only says "The plan stays as it is" when the list is empty. The eve's final reviews go to topics by `eveRank()` (behind plan first, then unquizzed/on-track by weight, clearly strong last), so a result that changes nothing doesn't move the eve slot.
- **Points per hour** `topicPoints()` / `pointsTable()`: exam points per topic (from AI-found old-exam tasks `e.oldTasks`, else the last scored mock, else old-exam hits, else weights) and points per remaining study hour. Each exam has `mode` (`"top"` default, or `"pass"` with `passPct`, default 50). `learnOrder()`: the **material order** (the topic list, which the AI returns in learning order) is the default sequence; repair topics (`extraMin > 0`) first. Top grade = material order. Pass = the topics `pointsTable()` marks as needed (cheapest points per hour until the pass mark) first, in material order, then the rest in material order. `topoOrder()` then pulls each topic's prerequisites in just before it, so links override the material order (pass mode also marks unfinished prerequisites of needed topics as needed, `r.first`). "Hours left" for a learned but not mastered topic = effort × (1 − level), rounded to half hours. The built-in example exams have prerequisite links (`exampleTopics()`). Shown under Exams & materials → "Where your time pays off".
- **Prerequisites** `t.prereqs` (topic ids this topic builds on; "Builds on" multi-select in the topics table, `t.prereqsSet` once the student edits it). `cleanPrereqs()` (called by `normExam()`, after analysis and topic removal) drops unknown/self links and breaks cycles: hand-set links first, then links to earlier topics, then later ones. Root-cause diagnosis in `quizEffect()`: if a below-plan topic has a weak prerequisite (`weakPrereq()`: quizzed below target −10, or not quizzed and not fully learned), most of the repair time and tomorrow's repair review go to the prerequisite, the topic itself is reviewed the day after, and the log says "Your trouble with X probably comes from Y — reviewing Y first." Mock exams process topics prerequisites-first and repair a prerequisite only once (`ctx.repaired`).
- **Mock exam scoring** `vMock()` / `applyMockResult()`: points per task (pre-filled from old-exam tasks, last mock or topic estimate), mapped to topics; per-topic % go through `quizEffect()` (the shared core of `applyQuizResult()`) against target × learning progress, like a quiz (a half-learned topic still has its learning time planned, so it isn't repaired twice), logged as one `kind: "mock"` plan change. Stored on the block as `b.mock` (with the energy level of that day's check-in) plus `b.mock.fx`: per topic the extra minutes added and mastery / repair-review date before and after. A scored mock can't be undone (Undo shows a message); "Edit results" on the results view calls `reverseMock()` (subtracts the extra minutes, restores mastery and review date unless a later quiz changed them, removes its quiz entries by `mockId`) and then applies the new points. Mocks scored before `fx` existed can't be edited. `replan()` places no new mock once one for that exam is done or scored. Per-topic mock results go into `t.quizzes` with `mock: true`, so they count for mastery but not for the review's quiz trend. Only real quizzes and Teach the AI / oral exam results go through `logQuiz()` (which records the energy level) into `fp.quizLog`.
- **Learning profile** `fingerprint()`: method retention (quiz 2 days after finishing a topic), forgetting speed (immediate vs. retention score → second review gap), time of day, plan completion rate, focus span (Pomodoro sessions), confidence calibration (sure/unsure/guess on quiz answers), enjoyment ratings, energy vs. results. `loadDemoFingerprint()` adds clearly marked example data (`demo: true`). Topics with a learning block done as a "Go lighter" session (`b.light`, see `wentLighter()`) are left out of the method comparison: their quizzes are logged with `light: true` and don't count for method retention, immediate scores or pending checks, so `assignMethods()` isn't skewed.
- **Energy check-in**: `startFocus()` (timer phase `checkin`) and the Study page ask low/OK/high once per session; entries go to `S.fp.energy` and are matched to blocks by id or topic+type (re-planning changes block ids). Quizzes within 4 h and focus sessions carry the level. Low energy offers a lighter session (flashcards instead of new material via `studyMethod()`, `lightFocusMin()` Pomodoro).
- **Post-exam review**: after an exam date passes, the Today page asks for the result: an optional Austrian grade 1–5 (`e.review.gradeNum`, `GRADES`), a free-text result (`grade`) and what helped/didn't, with frozen `examStats()` (study time, quiz trend, best method, readiness, latest mock score). At least one of the two grade fields is needed. The summary shows the numeric grade next to the readiness the plan predicted, and the mock score if there is one (`reviewStats()` adds a mock scored after the review). "Start a new semester" (`startSemester()`) moves finished exams to `S.archive` (incl. topic ids, `oldTasks`, mode/pass mark and every scored mock as `mocks`), deletes their blocks and material texts, and keeps `S.fp` (past block counts go to `fp.realismPast`). `normalize()` → `normExam()` / `normSemester()` fill defaults for all of this, also for restored backups.
- **Restored backups**: `normalize()` coerces block `status`/`type`/`minutes` and mock task points, drops a malformed `mock.fx`; `statsList()` and `blockRow()` also coerce numbers (`numOr()`) and escape ids, so crafted backups can't inject markup.
- **Today page**: "Did you do these?" only lists past open blocks of exams that are still ahead; a finished exam gets its review form instead.
- **Mobile (≤ 560 px)**: the tabs wrap onto their own row under the brand; the mock form shows each task as a small card (`#mk-table` CSS, `data-label` on cells); `renderTimer()` sets `--timer-h` on `<body>` so `main` gets bottom padding for the open timer.
- **AI calls**: always through `AI.json(prompt, opts)` → `aiCall()` → POST `/api/ai`, which returns server-sent events in Anthropic's format (`content_block_delta`, `message_delta`, `error`). Errors are objects `{ code, detail, fallbackTried }`; user-facing text comes from `aiError()` (busy: "The AI service is overloaded right now (this happens on the free plan at busy times). Your work is kept — try again in a minute."; `stream_broken`: "The connection to the AI broke off. Your work is kept — try again."; `rate_limited` with `fallbackTried` (the backend's error event has `fallback: true`): "The free AI quota is used up for now (a quicker backup model was tried too)…"), which never names the provider, hosting or env vars ("Ask the person who runs this Exam Coach…"); `aiDetail()` strips product/host names from the technical detail. `aiCall()` gives code `stream_broken` when reading the stream throws half-way (reset) or the stream ends without a stop reason or error event (the backend always sends one of them).
- **Material extraction** `extractFile(file, onPage)`: PDFs are read page by page with pdf.js; each page has its own try/catch and a 20 s timeout (`PAGE_TIMEOUT_MS`), a failing page is counted in `failed` and the others are kept (only if *every* page fails is the file refused). Returns `{ text, pages, noText, failed }`; `addFiles()` shows progress ("Reading "x.pdf" (file 1 of 2): page 40 of 130…", `busy.upload`, `uploadProgress()`), stores `noText`/`failed` counts and `src: { size, mod }` on the material, and says per file how many pages had no text ("65 of 130 pages had no readable text (probably pictures). The text on the other pages is used."), which pages failed, and if the file was cut. `capText()` cuts at `MAT_MAX` (400k) on a page boundary and records `keptPages` ("first 190 kept"). **"No text found"** (`looksEmpty(text)`, computed from the page markers in the stored text): under 50 non-space characters in total, or text (≥ 4 characters, `hasText()`) on at most 5 % of the pages (≥ 10 pages). The old rule (fewer than 25 characters per page on average) flagged real slide decks with many picture slides as scanned — measured with `tests/fixtures/figure-deck.pdf` (130 slides, text on 65). `recheckMaterials()` (on boot) re-evaluates materials flagged by the old rule. `cleanPdfText()`: Office writes Symbol-font characters as private-use codes U+F020–F0FF (measured: pdf.js 3.11 passes them through), these are mapped to Greek letters/math signs (`SYMBOL_PUA`), a lone one at a line start becomes "•" (Wingdings/Symbol bullets); ligatures ﬁ/ﬂ… are expanded and control characters (big brackets from TeX fonts) removed. pdf.js already maps the standard Symbol font and TeX math fonts (CMMI) to Greek correctly; what it cannot fix is formulas drawn as images or fonts without any usable mapping (then the AI is told to infer, see below). Test PDFs come from `tests/fixtures/make-pdf-fixtures.py` (reportlab).
- **Math notation** `mathText()`: the AI sometimes answers with LaTeX ("$X_{ii}$"). `AI.json()` appends `MATH_RULES` to every prompt (write Unicode math, never LaTeX/$; PDF formula text may have lost Greek letters or sub/superscripts, infer from context, describe in words when unclear, don't invent notation) and passes every string of the answer through `mathDeep()` → `mathText()` (Greek and common symbols, `_{…}`/`^{…}` → Unicode sub/superscripts or `^(…)`, `\frac{a}{b}` → a/b, `\sqrt`, `\hat`, `\mathbb`, `\text`, `\left/\right`; `$…$` only when it holds LaTeX or a single letter and has no space just inside the dollars and no digit right after the closing one, so "$5 and $10", "earns $5 and its profit π_B is $10" and "echo $PATH_VAR and $HOME" stay; `X_{…}`/`X^{…}` outside `$` look at the base by lookbehind, so stacked scripts convert too (`τ_{ij}^{1-σ}` → τᵢⱼ^(1−σ), `\sum_{i=1}^{n}` → ∑ᵢ₌₁ⁿ); `\binom{n}{k}` → C(n, k); recovers `\tau`/`\frac`/`\beta`/`\forall`/`\tan`/`\bullet`/`\binom`/`\rangle`/`\neq`… whose backslash JSON turned into a tab/form feed/backspace/CR/new line (`TEX_LOST`; "\ne" only before a space, so a new line before "e.g." stays)). `parseJSON()` doubles single backslashes that are not valid JSON escapes ("\alpha") before giving up. `normExam()` cleans topic names/summaries/goals/key terms/style saved before this. Because it is applied in `AI.json()`, the rule and the conversion cover every AI request: analysis (incl. goals/terms), quizzes, study material, teach/oral, grading and the practice exam.
- **Course folder** ("Add a whole folder", section `course folder`): with `showDirectoryPicker` (Chromium) the folder is walked recursively (`walkDir()`, hidden entries skipped, max depth 8 / 1500 entries); otherwise `<input type=file webkitdirectory>` (`#mat-folder`, `folderFromInput()`). Only PDF/TXT/MD are offered, others are counted as skipped. `folderPick` holds the list shown by `folderPanel()`: checkbox (pre-ticked unless added before) and type per file, guessed by `guessKind()` from the file name first, then the nearest folder name that says something (exam/Klausur/Prüfung/old/mock → Old exam; slide/Folie/lecture/Vorlesung/VO → Slides; else Script; "Prüfungsvorbereitung", "prüfungsrelevant", "exam prep", "Prüfungsstoff" don't count as old exam: `NOT_OLD`). Office lock files (`~$…`) are skipped. The same file (name + size + last change) found twice is listed unticked with "same file as <path>" (`x.dup`); ticked files whose names clash (with each other or an existing material) are stored under their relative path (`m.src.name` keeps the file's own name for `fileKey()`). A walk cut at 1500 entries says "first 1500 shown" (`folderPick.cut`); files that couldn't be opened are listed (`folderPick.failed`, also in the "no new files" toast). While `busy.upload || busy.folder` (`filesBusy()`), Analyse, Choose files and the folder buttons are disabled (labels get `aria-disabled`) and `addFiles()` / `readFolder()` / `analyzeMaterials()` return. Files count as added before by name + size + last change (`fileKey()`, from `m.src` and `e.seenFiles`, so removed files aren't offered again by the check). With the picker, the handle is kept in memory (`dirHandles`) and IndexedDB (`dir-<exam id>`; `e.folder = { name }` in the state) and "Check "name" for new files" (`checkFolder()`, asks for read permission again if needed) lists only new files. The handle is deleted with the exam. No network access, so no CSP change.
- **Material analysis** `analyzeMaterials()`: materials up to `ANALYZE_CHARS` (80k characters) go in one request; longer ones are split at page markers into parts (`splitMaterials()`), read one after another with progress ("Reading part 2 of 5…"), and merged by normalised topic name (`mergeTopics()`: highest weight, effort added up, `buildsOn` prerequisite names joined over all parts and mapped to topic ids in `analyzeMaterials()`). Old exams up to 40 % of a part go into every part so weights still come from them. On `prompt_too_large` it retries once with smaller parts (`ANALYZE_RETRY_CHARS`). If a part fails with `busy`/`rate_limited`/`stream_broken` (after the backend's own retries), the page waits `ANALYZE_BUSY.waitS` (20 s, countdown "The AI is busy — trying part 2 again in 20 s…" / "The connection to the AI broke off — trying part 2 again in smaller parts in 20 s…") and tries that part up to `ANALYZE_BUSY.tries` (2) more times. On `stream_broken` the retry uses smaller parts, once per run: if nothing was read yet, the whole plan becomes `splitMaterials(mats, ANALYZE_RETRY_CHARS)`; otherwise `smallerParts()` re-splits the failed part and all later ones (room = `ANALYZE_RETRY_CHARS` − shared old exams, at least 10k; shared old exams stay shared, parts already read are kept). If it still fails, the parts read so far stay in memory (`analysisResume` = `{ key, parts, shared, results, smaller, retry }`, keyed by `analysisKey()` = exam id, material ids/kinds/lengths; the parts themselves are stored, so a re-split run resumes with the same smaller parts), the message says how many parts were read, and pressing Analyse again continues from the failed part (only if the materials didn't change). `ANALYZE_CHARS` stays at 80k on purpose (see "Stream resets" below). An analysis that needs more than `ANALYZE_ASK_PARTS` (8) parts asks first ("This needs about N AI requests and may take a few minutes. Continue?", `busy.anAsk`, `#analyze-confirm`, actions `analyze-go` / `analyze-no`); a resume doesn't ask again. Files with (almost) no text (`looksEmpty()`, see Material extraction) are flagged on upload and skipped; if nothing readable is left, no request is sent. Up to 400k characters are kept per file (`capText()`). The analysis also returns the tasks of the most recent old exam (label, topic, points) → `e.oldTasks`; across parts `mergeTasks()` joins them by normalised label (old exams shared into every part are not multiplied; split old exams are collected in order) and takes the topic from the latest part that names a final topic.
- **Study modes** (Study page, panel "Check yourself", `modePanel()`): "Teach the AI" (Feynman: the student explains, the AI plays a curious classmate and returns reply, what was explained well, gaps with material sources, 1–2 follow-up questions and a 0–100 score; answering the questions gives a second, final score) and "Oral exam practice" (3–5 examiner questions one at a time, `ORAL_MIN`/`ORAL_MAX`, adapted to the answers; ends with a 0–100 score, mapped to the Austrian grade by `gradeFromScore()`). Sessions live in memory in `SM`, keyed by topic id; every AI call sends the whole transcript (`teachPrompt()` / `oralPrompt()`, material via `topicContext(e, t, MODE_CTX)` = 24k chars), so on an AI error the transcript stays and "Try again" re-sends (`modeStep()`); Stop gives the last answer back to the text box. `finishMode()` logs the result like a quiz: `applyQuizResult(e, t, score, missed, "teach"|"oral")` → `quizEffect()` with `src` (so target × progress comparison and root-cause prerequisite repair apply as for a quiz; marks `via` on `t.quizzes` and the log entry) and `logQuiz()` with kind `"teach"`/`"oral"`. Because the plan is rebuilt, `finishMode()` moves `studyId` to the topic's new block. **Method model decision:** "teach" is *not* a new entry in `METHODS`. Methods are how a topic is learned and are compared by quizzes right after learning and 2-day retention checks; a sixth method would become "untested" and make `assignMethods()` route the next topics into it and restart calibration (checks needed 10 → 12) for every student. "Explain it back" already is the Feynman method. So teach/oral results count for mastery, the feedback loop, quiz trend, time of day and energy, but not for the method comparison or as retention checks: `fingerprint()` only uses kinds `"immediate"`/`"retention"` (and skips `light`), and teach/oral never clear `t.checkPending`. AI errors use `aiError()` like everywhere else. Largest request: oral exam with 5 answers ≈ 24k material + ≤ 20k answers + transcript ≈ 50k characters, well under the backend's 200k limit; one request per student action. Optional speech input (`micStart()`) is only offered when `SpeechRecognition`/`webkitSpeechRecognition` exists; it needs `microphone=(self)` in the Permissions-Policy (no CSP change: the browser's recognition service is not a page request).
- **Topic goals and key terms**: the analysis asks per topic for 3–6 `goals` (`{ text, pages }` → stored as `t.goals = [{ text, src }]`, max 8) and 3–8 `terms` (`t.terms`, max 12). `cleanGoals()` / `cleanTerms()` (via `normExam()`) accept strings, drop empties/duplicates and cap lengths. `mergeTopics()` joins them over chunked parts in material order (repeats once); a re-analysis without goals keeps the old ones. The example exams have goals (`EXAMPLE_GOALS`). `studyBase()` sends the goals to the study/teach/oral prompts; the practice exam prompt sends them too.
- **Block content** `blockDetail(b)` → `{ covers, todo, result, terms }`, shown by `detailHtml()` in every planned block row (`blockRow(b, { detail })`, off in "Did you do these?"), on the Study page and in the calendar export (`detailText()`). Learn: the block's goals with pages, the method's concrete instruction and expected output (`DO`), key terms, old-exam tasks of the topic; the topic's last learn block adds "Then take the quiz". Reviews by `reviewKind()` (from the label: final / check / spaced / repair / quiz / practice) name what to review (weak concepts, goals) and the result; the mock names the old-exam tasks with points (or points to the practice exam).
- **Plan page layout** (`vPlan`): "Do this now" card (`nowCard()`: first open block today with details and one primary button, or the next block), shortfall alerts, "Week by week" (`weekPlan()` / `weeksHtml()`: per week from today to the last exam, phase chip Learning / Practice and review / Final stretch, hours, topics learned with starts/continued/finished, exam practice, reviews/checks, mock, EXAM), then "Day by day" (3 weeks, "Show the full plan"), then Availability, calendar + backup, and `chatbotNote()` ("Why not just ask a chatbot for a plan?", also on the empty state). The Today page shows `nowCard()` too and, for an exam without topics, an `#noplan` alert with one button.
- **Guided setup**: `vEmpty()` explains the 4 steps. An exam without topics shows `setupSteps(e)` at the top of Exams & materials (name/date → upload files or a whole folder → analyse → see plan; done steps ticked, exactly one primary button on the next step; `focus-field` action). The first successful analysis of an exam switches to the Plan view by itself (`first` in `analyzeMaterials()`; the plan was already built by `commit()`). A failed analysis leaves `busy.anErr` → `#analyze-error` on the page ("no topics and no plan yet… Your files are kept"), not only a toast. "Where your time pays off" (`pphPanel`) is a folded `<details id="pph">` (`busy.pphOpen`), so it doesn't look like the plan.
- **Practice exam (all topics)** (`PX`, `vPractice`, view `practice`; buttons on the exam card, under Topics, and in the "Do this now" card for a mock): `pxAllocate()` gives questions per topic by `topicPoints()` (largest remainder; 8/12/16 questions), each topic's points are shared by its questions (≈100 points). `pxPrompt()` sends topic keys T1…, goals, weak concepts, old-exam tasks and style, plus material per topic via `topicContext()` within `PX_CTX` (40k chars in total, ≤ 8k per topic). Unknown topic keys are dropped. Time suggestion `pxMinutes()` (2/6/10 min per mc/short/calc). MC is graded on the page, written answers through `gradeOpenAnswers()` — **the one AI grading function, shared with `gradeQuiz()`** (prompt unchanged; hardening of the grader belongs there). Missed concepts go to `t.weakConcepts`. The result becomes a done block `{ type: "mock", practice: true, label: "Practice exam (all topics)" }` scored by `applyMockResult()` (one task per question), so each topic's % goes through `quizEffect()` like a mock (incl. `fx`, Edit results, log title "practice exam (all topics)"). A practice block doesn't cancel the planned mock (`mockDone` ignores it) and doesn't feed `lastMock()` / `topicPoints()`.
- **Rendering**: string templates per view (`vDashboard`, `vPlan`, `vExams`, `vQuiz`, `vYou`, `vStudy`, `vMock`, `vPractice`, `vHistory`), one delegated click/change/input handler on `#main` using `data-act` attributes. Escape all user/AI text with `esc()`.

### Backend (netlify/edge-functions/ai.js)

- Providers: `gemini` (default, free tier) and `anthropic` (paid). Chosen by `AI_PROVIDER`, otherwise by which key exists.
- Env vars (set in Netlify → Project configuration → Environment variables): `GEMINI_API_KEY` (set on the live site), optional `ACCESS_CODE`, optional `ALLOWED_ORIGINS` (comma-separated extra origins allowed to call `/api/ai`), `GEMINI_MODEL` (default `gemini-3.8-flash`), `GEMINI_MODEL_QUICK` (default `gemini-3.5-flash-lite`), `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, `ANTHROPIC_MODEL_QUICK`.
- The response stream starts immediately (`: connected`) with a keep-alive comment every 5 s (`STREAM.keepAliveMs`), because Netlify cuts off functions that don't start answering within ~40 s. On 500/502/503/529 `fetchWithRetry()` retries up to 3 times after `RETRY.delaysMs` (2 s, 5 s, 10 s + up to 0.5 s jitter; ~18 s worst case, keep-alives keep flowing), then tries the quick model (`*_MODEL_QUICK`) once if it differs from the model asked for; if that fails too, the first model's error is reported. Each retry is logged with `console.log` ("Exam Coach AI retry: …"). Tests replace `RETRY.sleep` so they don't wait. Provider errors become `error` events with a code (`rate_limited`, `busy`, `bad_key`, `model_unavailable`, `prompt_too_large`, `upstream_error`) and a neutral message like `429 rate limit: …`; the full message with the provider name is logged with `console.log` (visible in Netlify's function logs).
- Hardening: body over 1.5 MB is refused (413) by `content-length` before parsing and again while reading (chunked); prompts over 200,000 characters too (the page's largest request is ~90,000: `ANALYZE_CHARS` + instructions). A browser `Origin` from another host gets 403 (no Origin = allowed). `ACCESS_CODE` is compared via SHA-256 + constant-time loop. Best-effort in-memory limits per client IP (`context.ip`): 120 AI requests/min (POST only; the GET status check never counts against it) and 30 wrong access codes per 10 min, generous because a whole class can share one university Wi-Fi IP. During a code lockout, requests carrying a code get 429, but a GET status check without a code still answers. Per edge isolate only, so not a real quota. `ACCESS_CODE` stays optional; whether to set one on the public site is the team's decision.
- A 429 (quota/rate limit) is not retried with the same model (those limits last a minute or a day); the quick model gets one try right away (free-tier quotas are per model), logged as "… answered 429 (quota or rate limit); trying … instead". If the fallback also fails, the first error is reported with `fallback: true` in the error event (`fetchWithRetry()` returns `{ res, fallbackTried }`; also set for the busy fallback).
- If reading the provider's answer fails half-way, the error event has code `stream_broken` ("The AI's answer broke off: …"). When the page closes the connection, `ReadableStream.cancel()` aborts the provider request (`signal` passed to `fetch` and `pipe()`), so no CPU is spent on an answer nobody receives.
- CPU budget (Netlify: 50 ms CPU per request; above it, or when the isolate dies, the page only sees a reset stream): the body is collected as bytes and decoded/parsed once (`readLimited()`), the provider request body is built once per model (Anthropic: cached per model; retries send the same string), and `geminiParser` is linear (searches only new text, joins an event's pieces once). Unhandled promise rejections would end the whole isolate (and every answer it is streaming): `drop()` catches `cancel()` rejections, and on Deno an `unhandledrejection` listener logs instead of crashing.
- Gemini's stream is converted to the same event format (`geminiParser`), thought parts are dropped, `responseMimeType: application/json`.

## Working conventions

- Keep it build-free: no frameworks, no bundler, no external CDNs (the CSP blocks them). Vendor any new library into `assets/vendor/`.

### Stream resets: what was measured and what is guessed

- **Measured locally** (Node, `process.cpuUsage()` around `handle()`, fake provider): largest allowed request (~199k chars, ~280 kB body with umlauts) + 4k-char answer ≈ 2–4 ms CPU; with a 120k-char answer ≈ 8–15 ms (incl. the test harness); first request in a fresh process ≈ 7–10 ms. Pieces for 280 kB: JSON.parse 0.4 ms, decode 0.3–0.5 ms, JSON.stringify of the provider body 0.5 ms, encode 0.2–0.3 ms. A normal analysis answer (a few kB) is negligible. So for the requests the page sends, CPU stays well under 50 ms.
- **Found**: the old `geminiParser` appended to one buffer and re-ran `replace`/`indexOf`/`slice` on it for every network piece: quadratic in the size of one event. One 200 kB event in 256-byte pieces cost 31–57 ms CPU (over the limit on its own); now 0.7 ms. Big single events happen when Gemini sends a JSON answer in one chunk; analysis answers are usually smaller, so this is a possible but not proven cause.
- **Guessed, not verifiable without Netlify logs**: the isolate being stopped (CPU limit, an unhandled rejection, platform recycling), or a network drop on the student's side during a 1–2 minute request. Netlify documents only the 40 s header timeout and 50 ms CPU; no wall-clock limit for a streaming response. Look in Netlify's function logs for "Exam Coach AI" lines around the time of a reset.
- **Why `ANALYZE_CHARS` stays 80k**: CPU doesn't depend on it in a relevant way (≈1 ms per 100 kB). Halving it would double the requests per analysis (130-page deck: ~3 → ~6) on the one key the whole class shares (requests-per-day quota), and the topic merge gets worse with more parts. The per-minute token quota is now handled by the quick-model fallback, and a part that breaks off is retried in 26k parts automatically, so smaller requests are used exactly when big ones fail.
